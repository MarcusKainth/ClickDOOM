# Splitting end-to-end batch overhead

An end-to-end batch costs more per instruction than the fold in isolation.
This harness splits that difference into its two candidate sources. It never
produced a recorded result.

## Question

The gap between end to end and the fold in isolation has two candidate
sources. Which of them carries it?

1. State reload. The extra work an end-to-end batch does over a select-only
   fold: the subquery reading the previous batch's pc, registers and icount,
   plus materialising the fold's result into `batch_commit` with
   `INSERT ... SELECT` instead of returning it to the client. RAM and decode
   materialisation is identical on both sides and cancels out of the
   subtraction.
2. Write-log flush. The two statements the end-to-end loop adds after the
   batch `INSERT`: merging the write-log into `ram`, which scales with
   write-log length, and deriving the `cpu_state` row, which is constant
   time.

## Method

Both flushes are generated by the production commit generators rather than
by a stand-in, so the measurement cannot drift from what a real flush does.
The fold SQL comes from the production generator in both its select-only and
end-to-end forms, and `batch_commit`'s first row is seeded by the production
bootstrap script.

The run creates and drops its own private database. Every table's DDL is
generated from the real schema with the database name rewritten, so it
cannot drift from the schema the CPU maintains, and only the synthetic
instruction mix is added on top. Isolation was adopted after a first version
targeted a shared database and was silently corrupted mid-run by another
process issuing DDL cycles against those same tables.

Two checks decide whether a run is reportable.

- The run brackets its own `system.query_log` window and counts DDL
  statements against its own database inside it. Any hit means the isolation
  did not hold, and the run aborts without printing numbers.
- Retired instructions must equal K times the batch count. A shortfall with
  a clean isolation check means a real halt in the synthetic mix, and the
  run aborts.

Both checks had a false positive worth carrying forward. Taking the window
boundaries at whole-second granularity let the run's own setup DDL fall
inside the window whenever setup finished in the same second, which fires
only on fast runs at small K, which is exactly when someone is iterating.
The boundaries are read at microsecond resolution instead. Separately,
`system.query_log` truncates very long logged query text and appends a
literal `(truncated N characters)` marker, and the fold's SQL is well past
that limit, so matching on the bare keyword `TRUNCATE` matched the run's own
queries through that marker. The guard matches DDL statement forms such as
`TRUNCATE TABLE` instead.

Output is TSV with one row per component: the select-only fold, the
end-to-end `INSERT INTO batch_commit`, the state-reload difference between
them, each of the two flushes, and their sum, each with total seconds and
microseconds per instruction over K times the batch count.

## Conditions

| | |
|---|---|
| Date | no result recorded |
| K | 50,000 by default |
| Batches | 12 by default |
| HWM | 20,000 by default |
| Database | private, created and dropped by the run |

## Results

No result was ever recorded for this harness. It has a runnable method and
no numbers.

The figure it was built to split was measured separately, at K = 50,000 on
ClickHouse 26.3: the fold in isolation cost 537.5 us per instruction and end
to end cost 862.6 us, leaving 325.1 us per instruction, 37.7% of end to end,
unattributed between state reload and write-log flush. That measurement did
not use this harness and does not split the 325.1 us.

## Verdict

None. The split was never measured here.

Per-statement attribution of a real end-to-end batch against the real ROM
was measured later by a different instrument, and it puts the fold at 99.86%
of a batch with the whole commit path at about 1%.
[`batch-attribution.md`](batch-attribution.md) is that measurement.
